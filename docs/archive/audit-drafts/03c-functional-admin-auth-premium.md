# Functional Integrity Audit — Part C: Admin Panel, Auth/Session, Premium/Payment/Vipps

Scope: `app/admin/*`, `lib/admin/*`, `app/api/admin/*`, NextAuth config (`lib/auth/config.ts`), session helpers, `app/api/payment/*`, `app/api/auth/vipps/*`, premium gating across match/journey/chat.

## Admin Panel

### What exists
- **Pages** (`app/admin/*`): `page.tsx` (root/redirect), `dashboard`, `users`, `matches`, `journeys`, `chat`, `conversations`, `analytics`, `resonance`, `system`, `system/status`, `logs`, `journey-content`, `tools`, `login`.
- **Data layer** (`lib/admin/data.ts`, 539 lines): read-only query helpers for admin stats, users, profiles, matches, conversations, insights (`getAdminStats`, `getAllUsers`, `getUserById`, `getAllProfiles`, `getProfileById`, `getAllMatches`, `getMatchById`, `getAllConversations`, `getConversationById`, `getAllInsights`, `getInsightById`).
- **Support libs**: `lib/admin/audit.ts` (audit log read/write helpers built on `prisma.auditLog`), `lib/admin/security.ts` (failed-login/rate-limit/audit dashboards), `lib/admin/requireAuth.ts` (admin auth helpers), `lib/admin/adminSystem.ts`, `notifications.ts`, `ai.ts`, `conversation.ts`, `observability.ts`, `realtime.ts`, `analytics.ts`, `system.ts`.
- **Destructive/mutating API routes**:
  - `PATCH /api/admin/users/[id]` — actions: `flag` (ban), `unflag`, `reset-onboarding`, `reset-journey`, `force-match-end`.
  - `POST /api/admin/matches/[id]/unmatch` — force-unmatch.
  - `POST /api/admin/matches/[id]/reset` — reset match to `pending`.
  - `POST /api/admin/journey/[id]/reset` — wipes `JourneyProgress` + deletes all `JourneyMilestone` rows for the user.
  - `POST /api/admin/journey/[id]/complete` — force-marks onboarding step 999.
  - `POST /api/admin/journey/[id]/next-step` — legacy no-op stub.
  - `POST /api/admin/conversation/[id]/freeze` / `unlock` — freeze/unfreeze a conversation.
  - `POST /api/admin/setup` — bootstraps an admin user (see below).

### Audit logging — inconsistent, not centrally enforced
`lib/admin/audit.ts` defines a proper `recordAdminAction(adminId, action, metadata)` that writes to `prisma.auditLog` with a typed `AuditAction` enum, plus `getAuditLogSummary`/`getAuditLogs` for reading. **However, `recordAdminAction` is never called anywhere in the codebase** (grep across `app/` and `lib/` returns zero call sites — only the definition in `lib/admin/audit.ts` itself). This means the "proper" audit trail table (`AuditLog`) is populated only by two unrelated call sites (`app/api/auth/vipps/callback/route.ts` lines 163-169 and 191-197, which log `ADMIN_LOGIN` for **regular Vipps user registration/login**, not admin actions — a semantic misuse of the action enum) and is otherwise dead code for actual admin moderation actions.

Instead, admin routes use an ad-hoc, per-file `logSystemLog()` helper (defined locally in `app/api/admin/users/[id]/route.ts` lines 21-27) that writes free-text messages into `prisma.systemLog` (level INFO) rather than the structured `AuditLog` table:
- `flag`/`unflag`/`reset-onboarding`/`force-match-end` in `app/api/admin/users/[id]/route.ts` call `logSystemLog(...)` — **logged**, but into the generic system log, not the audit log, and swallowed on failure (`catch { /* SystemLog feil skal ikke krasje operasjonen */ }`, line 26) — an audit-log write failure is silently ignored, so a destructive action can succeed with **zero record** if the systemLog insert fails.
- `reset-journey` (same file, line 76-81) — **NOT logged at all**. It wipes and recreates `JourneyProgress` inside a transaction but has no `logSystemLog` call, unlike its sibling actions in the same switch statement. This is an inconsistency/bug: every other case in the switch logs, this one doesn't.
- `app/api/admin/matches/[id]/unmatch/route.ts` and `.../reset/route.ts` — **no audit/system log at all**. These force-unmatch/reset a match with zero trace of which admin did it or when.
- `app/api/admin/journey/[id]/reset/route.ts` — **no audit log**, and notably **no admin-auth check at all** (see below).
- `app/api/admin/journey/[id]/complete/route.ts` — calls `requireAdmin()` from `lib/auth/security` (a different helper than the rest of the admin routes use) but has no audit log.
- `app/api/admin/conversation/[id]/freeze` and `/unlock` — DO log to `systemLog` (lines 42/40 respectively) including admin id, which is good, but still not using the structured `AuditLog` table/`recordAdminAction`.

**Functional gap**: There are two parallel, inconsistent auth mechanisms in use across admin API routes:
1. `requireAuth` from `@/lib/auth/requireAuth` + `castToAdminUser` (used in `users/[id]`, `conversation/[id]/freeze`, `conversation/[id]/unlock`).
2. `adminAuthGuard()` from `@/lib/auth/adminAuthGuard` (used in `matches/[id]/unmatch`, `matches/[id]/reset`, `conversation/[id]/route.ts`).
3. `requireAdmin()` from `@/lib/auth/security` (used in `journey/[id]/complete`).
4. **No auth check whatsoever** in `app/api/admin/journey/[id]/reset/route.ts` (`app/api/admin/journey/[id]/reset/route.ts:1-55`) — this route deletes all `JourneyMilestone` rows and resets `JourneyProgress`/`onboardingComplete` for an arbitrary user ID with **no admin/session check of any kind**. Any authenticated (or even unauthenticated, depending on middleware matching — `/api/admin/*` IS in `PROTECTED_API_PREFIXES` in `middleware.ts`, so at minimum a valid NextAuth session cookie is required, but **not an admin role**) caller can wipe another user's onboarding/journey state by ID.
   - Cross-check with `middleware.ts`: `/api/admin` is in `PROTECTED_API_PREFIXES`, which only checks `hasValidSession(req)` (cookie presence), **not role**. Role-based admin gating in middleware only applies to page routes under `/admin/*` (`ADMIN_PREFIX`), not to `/api/admin/*`. So **any logged-in non-admin user** can call `POST /api/admin/journey/[id]/reset` (and similarly under-guarded API routes) directly, bypassing the UI entirely, since the route itself performs no role check.
   - `app/api/admin/journey/[id]/next-step/route.ts` similarly has zero auth check, though it's currently a no-op stub ("Legacy endpoint - no action taken") so the impact is currently nil — but it's still exploitable dead code with the wrong permissions model.

### Confirmation step: UI-only, not enforced server-side
- `app/admin/users/page.tsx` (lines 194-215, 244-286) implements a client-side `confirmAction` state with a "Bekreft/Avbryt" dialog before calling `performAction()` → `PATCH /api/admin/users/${userId}`. This is a **good UX pattern but purely cosmetic protection**: the actual `PATCH /api/admin/users/[id]` API route has no second-factor, no re-auth, no idempotency token, and no rate limiting specific to destructive actions. Any direct API call (e.g., via curl with a valid admin cookie, or via CSRF if cookies are not `SameSite=strict`) executes the action immediately — flag/unflag/reset-onboarding/reset-journey/force-match-end are all one-shot, irreversible-in-effect actions with no "are you sure" at the server layer.
- `app/admin/matches/page.tsx` has **no confirmation dialog at all** for any destructive action, and in fact the matches admin page (`app/admin/matches/page.tsx`) doesn't even render buttons to call `unmatch`/`reset` — those routes exist server-side (`app/api/admin/matches/[id]/unmatch/route.ts`, `.../reset/route.ts`) but appear to be **orphaned/unwired from any UI** (no `fetch` call to `/unmatch` or `/reset` found anywhere in `.tsx` files). This means these force-unmatch/reset-match capabilities are either dead code or invoked out-of-band (e.g., manual API testing) with no UI, no confirmation, and no audit trail — a genuinely dangerous combination if ever wired up later without adding the missing safeguards.
- Similarly, `app/api/admin/journey/[id]/complete`, `/next-step`, and `/reset` have no corresponding UI wiring found in `app/admin/journeys/page.tsx` or elsewhere (not confirmed to be dead, but not visibly reachable from the audited admin pages).

### `app/api/admin/setup/route.ts` — functional behavior
`POST /api/admin/setup` (61 lines):
1. Checks if a user with hardcoded email `admin@tosom.no` exists in the DB.
2. If yes: returns `{ success: true, message: 'Admin-bruker finnes allerede', adminId }` — no-op, idempotent.
3. If no: **creates** a new `User` row with `email: 'admin@tosom.no'`, `name: 'Admin'`, `role: 'ADMIN'`, plus a nested `Profile` (`identityName: 'Admin'`, `age: 30`, `deepProfileStep: 'SUMMARY'`).
4. Returns the new admin's `id`/`email` in the JSON response body.

Functional notes (not security scoring, per instructions, but describing behavior):
- **No authentication/authorization gate on this route at all** — it is a bare `export async function POST()` with no session check, no secret/token requirement, no IP allowlist, nothing. It is reachable by anyone who can reach the API (subject to `middleware.ts`'s generic `/api/admin` prefix protection, which — as noted above — only requires *any* valid session cookie, not an admin role, and this specific route doesn't even use `requireAdmin`/`adminAuthGuard` internally).
- It creates a real `ADMIN`-role account with a fixed, publicly-guessable email and **no password is set on this user record via this route** — the actual admin login (`/api/admin/auth`) validates against `process.env.ADMIN_EMAIL`/`ADMIN_PASSWORD` env vars, a completely separate mechanism from the `User` table row this route creates. So this route creates a `User{role: ADMIN}` DB row that is *disconnected* from the actual admin-login credential check — meaning this endpoint's created "admin" user is functionally almost inert for the `/admin/*` panel (which uses the JWT-cookie/env-var flow), but it **does** grant `role: ADMIN` on a `User` record that IS respected by `requireAuth`/`isAdminRole` checks used in some `/api/admin/*` routes (e.g., `users/[id]/route.ts` uses `requireAuth` + role check against the NextAuth session, which reads `role` from the JWT which is set from the `User.role` field at sign-in time). This creates a confusing dual-admin model: (a) env-var-based admin login → `admin_token` JWT cookie, vs (b) DB `User.role = ADMIN` → NextAuth session with `role: 'admin'` claim. The `/api/admin/setup` route only ever provisions path (b), while the `/admin/login` UI only exercises path (a). It's unclear from the code whether a real operator flow ties these together (e.g., is `admin@tosom.no` ever actually signed in via magic-link/email to get a NextAuth session? No `EmailProvider` restriction excludes this email from getting a real magic-link session with `role: ADMIN` privileges, which is a functional/security overlap for the other subagent to weigh in on).
- Can be called repeatedly with no rate limit; idempotent in effect (won't create duplicates) but still executes a full DB round-trip (`findUnique` + potentially `create`) on every call with zero throttling.

### Other admin panel functional gaps
- `lib/admin/data.ts` — `getAllUsers()` (lines 164-218) computes `matchCount` by querying only `match.userAId` (`counts` query at line 192-196 filters `userAId: { in: userIds }` only), **ignoring matches where the user is `userBId`**. This under-counts matches for any user who was the "B" side of a match — a data-accuracy bug in the admin users list. Also `conversationCount` is hardcoded to `0` for every user (line 216) — dead/unimplemented field always shown as zero in the admin UI type (`AdminUser.conversationCount`), never actually computed anywhere in this file.
- `getUserById()` (lines 220-268) also hardcodes `matchCount: 0` and `conversationCount: 0` (lines 265-266) unconditionally — the detailed admin user view has **no match/conversation counts at all**, despite the type declaring them as real fields. This is dead/placeholder logic never filled in.
- `getAllProfiles()`/`getProfileById()` compute `deepProfileComplete` via `p.deepProfileStep === 'SUMMARY'` (lines 300, 320) — a fragile string-literal comparison duplicated in two places instead of using the canonical `user.deepProfileComplete` boolean field that exists on the `User` model elsewhere in the schema (see `AdminUser.deepProfileComplete` used directly in `getAllUsers`/`getUserById`). Inconsistent source-of-truth for the same concept between different admin views.
- Two entirely separate "get all users" implementations exist: `lib/admin/data.ts::getAllUsers()` (uses `bannedAt`/simple match count) and the actual route handler `app/api/admin/users/route.ts` (uses a richer query with `deletedAt`, `lockedUntil`, `matchesA`/`matchesB` counts, `journey` relation, `rejectedByB`/`rejectionReason`). It's unclear whether `lib/admin/data.ts` is dead code or used by some other unaudited page — but at minimum it represents **duplicated, drifted business logic** for the same admin capability, and if `app/admin/*` pages import from `lib/admin/data.ts` anywhere (not confirmed used from any `page.tsx` in this audit) they'd show subtly different/wrong numbers than the API-route-backed pages.
- `PATCH /api/admin/users/[id]` (`app/api/admin/users/[id]/route.ts`): `reset-journey` action (lines 76-81) deletes ALL `JourneyProgress` rows for the user then creates exactly one fresh row — functionally fine, but if the delete succeeds and the create throws (e.g., unique constraint race), the transaction rolls back atomically (good, it's wrapped in `$transaction`), but there is **no confirmation that any associated `JourneyMilestone` rows tied to the now-deleted `JourneyProgress` are cleaned up** — compare to `app/api/admin/journey/[id]/reset/route.ts` which DOES explicitly `deleteMany` milestones (line 44-46). Two different "reset journey" endpoints exist (`PATCH /api/admin/users/[id]` action=`reset-journey`, and `POST /api/admin/journey/[id]/reset`) with **different actual behavior** (one cleans up milestones, one doesn't) — functional drift between two code paths that claim to do the same thing.
- `force-match-end` (users/[id] route, lines 83-91) sets matched conversations' `endedAt` and matches' `status: 'ended'`, but does **not** notify either user, does not update `lastMatchAt`, and does not check whether the match/conversation records it's ending belong to matches that are already `ended`/`unmatched` (no idempotency guard) — calling this twice is harmless but wasteful (re-queries and re-updates already-ended records with no-op `data: {status: 'ended'}` writes).
- Self-protection is present (`if (targetUserId === adminUser.id) return errorResponse(...)` line 53) which is good — prevents an admin from banning themselves — but this same self-protection guard does **not** exist in `app/api/admin/matches/[id]/unmatch/route.ts`, `.../reset/route.ts`, or `journey/[id]/reset` — not directly relevant there (those act on match/journey IDs not user-self-action) but shows inconsistent defensive coding across the admin API surface.

## Auth & Session

### Config location and provider
`lib/auth/config.ts` — NextAuth v5, exports `{ handlers, auth, signIn, signOut }`.
- **Adapter**: `PrismaAdapter(prisma)` — database-backed `Account`/`Session`/`VerificationToken` tables exist in `prisma/schema.prisma`, but...
- **Session strategy**: explicitly `session: { strategy: "jwt" }` (line 41-43) — **JWT strategy, NOT database strategy**, despite having a Prisma adapter configured. This is a notable functional inconsistency: the `Session` Prisma model exists and is wired via `PrismaAdapter`, but with `strategy: "jwt"` the adapter's `Session` table is **never used for user sessions** (it's only relevant for `Account`/`VerificationToken` linkage in this config, e.g., magic-link flows). This means:
  - **No server-side session revocation is possible.** Since sessions are self-contained signed JWTs stored in a cookie, there is no DB row to delete to invalidate an active session. Banning a user (`bannedAt` set via `flag` admin action) does **NOT** invalidate their existing JWT session — they can continue using the site with full access until their JWT naturally expires, because nothing in `jwt()`/`session()` callbacks (lines 46-67) re-checks `bannedAt`/`deletedAt`/current `role` from the DB on each request. The JWT `role` claim is set **once, at login time** (`if (user) { token.role = ... }`, line 48 — only runs when `user` is present, i.e., on initial sign-in) and never refreshed afterward.
- **Provider**: Only `EmailProvider` (magic link) is configured (lines 21-38). `sendVerificationRequest` is overridden to just `console.log` the magic link URL instead of actually sending an email via the configured SMTP transport (comment at line 31-36: "Override to disable default Magic Link UI"). This means **the standard NextAuth magic-link path never emails the user** — it's fully custom/unimplemented at this layer (there's a separate custom phone-verification flow, per `app/api/auth/phone/*`, that manually calls `signIn('credentials', ...)` — but the main config has no `CredentialsProvider` registered at all (comment at line 7-8 explicitly says CredentialsProvider was removed), so that `signIn('credentials', ...)` call in `app/api/auth/phone/verify/route.ts:102` will **fail at runtime** because no credentials provider is registered in `config.ts`. Confirmed by the code itself falling back to a manual, non-NextAuth cookie (`next-auth.session-token`, sha256 hash of `user.id + secret`, plain unsigned-format cookie) in the `catch` block (`app/api/auth/phone/verify/route.ts:107-121`) — a fallback session mechanism that is **not a real NextAuth JWT** and would not be recognized/decoded correctly by `auth()` elsewhere in the app (NextAuth JWTs are encrypted+signed via `jose`, not a raw sha256 hex string). This is a functional bug: phone-verified users likely end up in a broken session state that middleware's `hasValidSession()` will treat as "has session" (since it only checks cookie *presence*, not validity — `middleware.ts` `getSessionToken`/`hasValidSession`, lines ~34-43) but subsequent `auth()` calls in actual API routes will fail to parse it, so the user appears logged in to the middleware gate but is effectively unauthenticated for real work.

### Session refresh / rotation
- No `session.maxAge`/`updateAge` configured in `config.ts` — NextAuth defaults apply (`maxAge: 30 days`, `updateAge: 24 hours` for JWT strategy). No custom rotation logic. No sliding-window re-validation against the DB.
- No `trigger === 'update'` handling in the `jwt()` callback — even if a client called `update()` from `useSession()` to force a session refresh, there's no logic to re-fetch `role`/ban status from the DB (the callback only branches on `if (user)`, which is only truthy on initial sign-in, never on manual refresh triggers). Confirmed no `useSession()`/`update()` calls anywhere in the client codebase (`grep` for `useSession\(\)` returned 0 results), so this gap is currently unexploited by any UI feature, but any future "refresh my session after role change" feature would find the callback structurally incapable of doing so.

### Role change while session active
- **Not handled.** If an admin promotes/demotes a user's `role` in the DB directly (there's no dedicated "change role" admin API route found in this audit, but the field is directly writable via Prisma), or if a user gets banned (`bannedAt` set), their existing JWT session **retains the old role/ban-state claims** until the JWT expires (default 30 days) or they explicitly sign out and back in. There is no server-side "force logout" or session-invalidation mechanism tied to admin moderation actions. This directly undermines the `flag`/`unflag` ban feature in the admin panel: banning a user sets `bannedAt` in the DB, but:
  1. No API route in `match`/`journey`/`chat`/`conversation` checks `bannedAt` at all (confirmed via grep — zero hits for `bannedAt`/`banned` in `app/api/match`, `app/api/journey`, `app/api/chat`, `app/api/conversation`).
  2. Even if such a check existed, the JWT itself doesn't carry ban-state, so any check would need a DB round-trip per request anyway — but currently **no such round-trip/check exists**, so `bannedAt` is **purely cosmetic in terms of actually restricting the banned user's platform access**. It only affects what the admin panel *displays* (red "Flagga" badge) and is used as a guard in the admin route itself (`if (targetUser.bannedAt) return errorResponse('Bruker er allerede flagga/banna', 400)` — i.e., it prevents double-banning, not the banned user's normal usage).

### Multi-device session handling
- With `strategy: "jwt"` and no database session table in use, each device/browser gets its own independently-signed JWT cookie with its own expiry. There is no concept of "list active sessions" or "revoke this device" anywhere in the codebase (no UI, no API route for session management found under `app/api/admin/session/route.ts` — let's note that route exists: `app/api/admin/session/route.ts`, but that's for the **admin's own** JWT admin_token, not for managing a regular user's multiple device sessions). Regular users have zero visibility or control over concurrent sessions from other devices; signing in on device B does not invalidate or even inform about device A's session.

### Sign-out behavior
- **Admin logout** (`app/api/admin/logout/route.ts`) is implemented: `DELETE` clears the `admin_token` cookie by setting `maxAge: 0`. Functional and correct for the JWT-cookie admin auth path.
- **Regular user logout is NOT implemented anywhere in the UI.** The only "Logg ut" (Log out) button found in the entire codebase is in `app/settings/page.tsx` (`<GoldButton fullWidth>Logg ut</GoldButton>`), and it has **no `onClick` handler at all** — it's a static button with a label and zero wiring to `signOut()` from NextAuth. Grep confirms zero calls to `signOut(` anywhere in `app/` `.tsx` files. This means **regular users have no functional way to sign out of the platform through the UI** — a significant functional gap. (NextAuth's default `/api/auth/signout` route technically exists via `handlers` export, but nothing in the app links to it or POSTs to it.)

## Premium/Payment/Vipps

### `create-checkout-session` — functional behavior
`app/api/payment/create-checkout-session/route.ts`:
- Requires auth (`createApiHandler(req, { auth: true, ... })`), rate-limited to 5 req/min.
- Accepts an optional `plan`/`successUrl`/`cancelUrl` body via a Zod schema that only allows `plan: 'premium'` — but **notably, none of the three actual payment UI pages send a `plan` field matching this schema**: `app/betaling/page.tsx` and `app/(auth)/onboarding/payment/page.tsx` both POST `{ planId: selected }` (field name `planId`, values like `'weekly'`/`'monthly'`/`'quarterly'`/`'annual'`) — the API's Zod schema (`CheckoutSchema`) only recognizes an optional field named `plan` (not `planId`) restricted to the literal `'premium'`. Since `body.planId` doesn't match any schema key, it's silently ignored (Zod's default behavor for unrecognized/unvalidated extra keys, assuming `.parse()` isn't in strict mode — confirmed no `.strict()` call), meaning **the user's actual plan selection (weekly/monthly/quarterly/annual with different prices show in the UI: 149/299/699 kr on `/betaling`, and 149/129/99 kr/mo on `/onboarding/payment`) is completely discarded** — the backend calls `createCheckoutSession(user.id, successUrl, cancelUrl)` (`lib/payment/stripe.ts`) with a single hardcoded `STRIPE_PRICE_ID` env var and `mode: 'subscription'`, ignoring plan choice entirely. This is a real logical bug: whichever of the 3-4 differently-priced plans the user clicks, Stripe checkout is created for one single fixed price — the UI plan-selection feature is non-functional/cosmetic.
- `createOrUpdateCustomer()` is called before `createCheckoutSession()`, but its return value (`customerId`) is **never passed into `createCheckoutSession()`** (`app/api/payment/create-checkout-session/route.ts:44-51` — the `customerId` variable is computed but unused in the subsequent call). This means every checkout session is created without an associated existing Stripe Customer (contradicts the `customer_email: undefined` comment in `lib/payment/stripe.ts:44` too — the customer creation step is entirely wasted work with no effect on the actual checkout session).

### Webhook — functional behavior
`app/api/payment/webhook/route.ts`:
- Validates Stripe signature correctly via `validateWebhook()`.
- Handles `checkout.session.completed`, `customer.subscription.updated`, `customer.subscription.deleted` — but in **all three cases, the handler only `console.log`s the event data and does nothing else**. The `checkout.session.completed` case has an explicit `// TODO: Oppdater subscription-status i databasen når Prisma-modell finnes` (line 44) — confirming there is **no Prisma model for subscriptions/premium status at all** in the schema (confirmed by schema grep returning zero hits for `isPremium`/`premium`/`subscription`/`Subscription`). This means: **even if a real Stripe payment succeeds end-to-end, nothing in the database is ever updated to reflect the user now being "premium."** The webhook is a complete no-op with respect to actual app state.

### Is premium gating enforced anywhere?
- Grepped `isPremium`/`premium` across `app/api/match`, `app/api/journey`, `app/api/chat`: **zero functional/logic hits** (the only `premium` string hits found platform-wide are decorative CSS/comment usages like "Premium Nordic Gold 2026" styling comments and a `PremiumCTAButton` component name — no gating logic).
- There is **no `isPremium` field on the `User` model** in `prisma/schema.prisma` at all.
- `lib/payment/stripe.ts::hasActiveSubscription(userId)` exists and correctly queries Stripe for an active subscription — but grep confirms it is **never called from anywhere else in the codebase** (only its own definition matches). It's dead code.
- **Conclusion: premium/payment gating is 100% cosmetic.** Every match/journey/chat/conversation API route is reachable by any authenticated user regardless of payment status. The entire "one price, no subscription tiers" marketing copy on `/priser` ("Ingen abonnement... ingen premium-pakker") is actually true in effect, but not by design — it's true because premium gating was simply never implemented anywhere in the backend, not because of an intentional pricing-model decision enforced in code. The `/betaling` and `/onboarding/payment` pages' `catch` blocks even explicitly bypass payment on error ("Fallback: fortsett til onboarding for dev" — `app/(auth)/onboarding/payment/page.tsx:88-89`, and similarly `app/betaling/page.tsx` swallows errors silently), so even the UI-level payment flow is designed to let users through regardless of whether Stripe checkout succeeds.

### Vipps authorize/callback — functional behavior
`app/api/auth/vipps/authorize/route.ts`:
- Correctly generates CSRF `state`, signs it via HMAC with `NEXTAUTH_SECRET`, stores `state.hash` in a `vipps_state` cookie (5 min TTL), and returns the Vipps authorize URL as JSON (not a redirect — caller must handle the redirect client-side).
- Returns 503 if `VIPPS_CLIENT_ID` isn't configured — appropriate for "Vipps not yet active" state per the roadmap.

`app/api/auth/vipps/callback/route.ts`:
- Verifies state (constant-time compare — good), exchanges code for access_token, fetches userinfo, then **creates or updates a `User` row directly via Prisma** — this is a **completely separate user-creation/session path from NextAuth's own OAuth flow**. It does not use `PrismaAdapter`'s `Account`/linking table at all (no `Account` row is created linking `vipps` provider to the user), meaning if a user later also has an `Account` row from a different provider (or from magic-link `EmailProvider`) with the same email, there's no `provider_providerAccountId` linkage — this hand-rolled flow **bypasses NextAuth account-linking entirely**.
- **Sets a custom cookie `tosom_session`** (line 210, HMAC-SHA256 of `user.id + '-vipps'`) that is **NOT a NextAuth JWT and is not recognized by `auth()`, `middleware.ts`'s `getSessionToken()` (which only looks for `authjs.session-token`/`next-auth.session.token`), or any other session-reading code in the app.** This means: after a successful Vipps login via this callback, the user is redirected to `/dashboard` with a cookie that **no other part of the application actually reads or validates**. Functionally, Vipps login via this route currently **does not produce a working authenticated session** for the rest of the app (dashboard/match/journey/chat API routes would all reject them as unauthenticated on the very next request, since `middleware.ts` requires `authjs.session-token`/`next-auth.session.token`, not `tosom_session`). This is a significant functional gap for the "Vipps planned but not yet active" roadmap item — the callback route exists and appears complete, but produces a session token in a format the rest of the app cannot consume.
- Misuses the `AuditLog.action` enum: logs regular user registration/login events as `'ADMIN_LOGIN'` (lines 163-169, 191-197) — semantically wrong (these are not admin logins), and `adminId` field is set to the *regular user's* `user.id`, not an actual admin — this pollutes the admin audit log with non-admin events and would make `getAuditLogSummary()`'s "suspicious admin actions" tracking inaccurate if ever surfaced in the admin security dashboard (`lib/admin/security.ts::getAuditLogSummary` counts `USER_BAN`/`USER_DEACTIVATE`/`CONTENT_DELETE` as suspicious — `ADMIN_LOGIN` isn't counted as suspicious currently, but conflates unrelated event types under one admin-focused audit table).

### What would need rework for Stripe removal / Vipps activation
1. **Payment-to-premium linkage doesn't exist at all today** — before removing Stripe, note that removing it changes *nothing* about actual app behavior since no route currently gates on payment status. This should be flagged: the "premium" concept needs to be designed from scratch (new `isPremium`/`subscriptionStatus`/`subscriptionExpiresAt` fields on `User` or a new `Subscription` model), plus gating middleware/checks added to match/journey/chat routes, if premium gating is actually desired going forward.
2. **`app/betaling/page.tsx` and `app/(auth)/onboarding/payment/page.tsx`** both call `/api/payment/create-checkout-session` (Stripe-specific) and display multiple differently-priced plans (weekly/monthly/quarterly/annual) that don't match the roadmap's single "349 NOK per period via Vipps" model (per `docs/tosom-concept-v2-skisse.md` / `docs/tosom-platform-map.html`). Both pages need to be rewritten to call a Vipps payment-initiation endpoint (which doesn't currently exist — only `/api/auth/vipps/authorize`+`/callback` exist for *login*, not *payment*) with the single fixed price, and the plan-selection UI (which is currently non-functional/discarded server-side anyway, per the bug above) should likely be removed entirely to match the "one price" positioning on `/priser`.
3. **`app/api/payment/webhook/route.ts` and `lib/payment/stripe.ts`** are Stripe-specific and should be deleted/replaced with a Vipps ePayment webhook handler; there is currently no Vipps payment (ePayment API) integration at all in the codebase — only Vipps **Login/OAuth** (`authorize`/`callback`) exists. Vipps payments and Vipps login are different Vipps products/APIs, and only the login side has been built.
4. **`app/api/auth/vipps/callback/route.ts`'s session cookie must be fixed** to actually integrate with NextAuth (either via a proper `CredentialsProvider`/custom provider registered in `lib/auth/config.ts`, or by having this route call `signIn()` server-side, or by switching middleware/session-reading code to also recognize `tosom_session`) — otherwise "activating" Vipps login will appear to work (redirect succeeds) but leave users functionally logged out for every subsequent authenticated action, matching the same underlying bug pattern already present in `app/api/auth/phone/verify/route.ts`'s fallback cookie path.
5. **Admin bootstrap (`/api/admin/setup`) and admin login (`/api/admin/auth`, env-var based) are entirely separate from the Vipps/NextAuth user model** — no rework strictly required for Vipps activation, but worth noting the dual admin-identity model (env-var admin vs. DB `User.role=ADMIN`) will need to be reconciled at some point regardless of payment provider changes.

### Step count: blueprint vs implementation — STILL MISMATCHED (documentation not yet reconciled, but a *different* mismatch now exists)

- **Verified in code**: `app/onboarding/OnboardingFlow.tsx` (lines 1–4, 227–241, 434) explicitly implements **13 steps** (`totalSteps = 13`, `stepsMeta` array has 13 entries, `case 0` through `case 12` in `renderStep()`). This matches the `app/onboarding/steps/` file count (Step1Profile, Step2Personlighet, Step2Livssituasjon, Step3Tilknytning, Step4Kjærlighetsspråk, Step5LivsstilVerdier, Step5Relasjonsstil, Step6FramtidVisjon, Step7HumorPersonlighet, Step8Grenser, Step8ModenNysgjerrighet, Step9Oppsummering, Step10StartReisen = 13 files).
- **The Prisma `DeepProfileStep` enum** (`prisma/schema.prisma`) still only has **9 substantive steps** (IDENTITY, LIFE_SITUATION, LIFESTYLE, PERSONALITY, RELATIONSHIP_STYLE, COMMUNICATION, INTIMACY, FUTURE_VISION, BOUNDARIES) + a `SUMMARY` terminal state — i.e., 10 enum values total, none of which correspond 1:1 with the 13 UI steps (the UI actually splits "Personlighet" and "Livssituasjon" into two steps, and "Livsstil" and "Relasjonsstil" into two steps, and "Grenser" and "Moden nysgjerrighet" into two steps — this is the documented "delte nummer" 2×Step2, 2×Step5, 2×Step8 pattern).
- **Conclusion: blueprint and implementation are NOT aligned.** The documentation issue described in `SECURITY-STABILITY-PLAN-v1.md` is still open — `docs/core/TOSOM_BLUEPRINT.md` line "Påkrevd onboarding (9 steg)" has not been updated to reflect the 13-step UI, and no code changes have reconciled the Prisma enum with the UI step count either. This is a live, unresolved documentation/implementation divergence, not just a historical note.

### CRITICAL — The dedicated onboarding API routes are dead/orphaned code; a completely different, less-secure path is actually used

This is the single largest functional finding in the onboarding area:

- `app/onboarding/OnboardingFlow.tsx` **never calls** `/api/onboarding/save`, `/api/onboarding/progress`, or `/api/onboarding/complete`. Searching the entire live codebase (`grep -rln "api/onboarding/complete\|api/onboarding/progress\|api/onboarding/save"`) shows these endpoints are referenced ONLY by:
  - `hooks/useAutoSaveForm.ts` (`/api/onboarding/save`) — and this hook itself is **never imported anywhere** in the app (confirmed via `grep -rln "useAutoSaveForm"` — zero results outside its own definition file).
  - `.next` build artifacts (irrelevant, generated).
- This means `app/api/onboarding/complete/route.ts`, `app/api/onboarding/progress/route.ts`, and `app/api/onboarding/save/route.ts` are **100% dead code paths in production** — fully-built, session-checked, Prisma-backed endpoints that no UI ever calls.
- Additionally, `hooks/useAutoSaveForm.ts` (lines 1–9) is itself broken: it POSTs a `FormData` body to `/api/onboarding/save`, but that route (`app/api/onboarding/save/route.ts` line 38) calls `await req.json()`, which will throw on a `multipart/form-data` body. Even if this hook were wired up, it would fail with a 500 (unhandled `SyntaxError` inside the try/catch — actually it IS inside a try/catch, so it would return the generic 500 "Kunne ikje lagre profil", masking the real bug).
- **What actually happens instead**: `OnboardingFlow.tsx`'s `handleStartReisen()` (lines 296–426) collects the ENTIRE 13-step form state client-side in memory/localStorage and sends it in **one single POST** to `/api/profile/setup` only at the very last step (Step 13 / "Start reisen"). This is confirmed by reading `app/api/profile/setup/route.ts`, which validates the whole payload with `validateOnboarding()` (Zod, `lib/validation/onboarding-setup.ts`) and upserts the `Profile` in one transaction.

### Consequence 1 — No true incremental server-side persistence; "resume after interruption" is a client-side-only illusion

- All 13 steps are holder in a single React `data` state object (`OnboardingFlow.tsx` line 182) and persisted only to `localStorage` under key `tosom_onboarding_draft` (`loadDraft`/`saveDraft`, lines 155–170), debounced 400ms (lines 196–204).
- **If the user clears browser storage, switches devices, uses a private/incognito window, or the browser evicts localStorage (e.g., iOS Safari's 7-day ITP purge for non-visited sites), all onboarding progress is silently lost** with zero server-side recovery — the server has no record of partial progress until the final "Start reisen" submission succeeds.
- This directly contradicts the documented intent in `docs/core/TOSOM_SUBSYSTEMS_OVERVIEW.md` / `docs/core/TOSOM_API_OVERVIEW.md`, which describe `POST /api/onboarding/save` as "Lagre onboarding-data for nåværende steg" (save per-step) and `GET /api/onboarding/progress` as fetching "pågående progresjon" (in-progress progress) — none of that documented behavior is actually wired up.
- The draft is only cleared from localStorage when `step > 11` (`OnboardingFlow.tsx` line 208) — i.e., once the user reaches the Oppsummering/Start-reisen steps — but if the final `/api/profile/setup` call fails (e.g., network error, validation error), the draft has already been cleared at step 12/13 transition regardless of whether the save actually succeeded, since the `useEffect` triggers purely on `step` value, not on save success. Actually verify: the effect clears when `step > 11`, which is triggered on navigating TO step 12 (Start reisen), not on successful submission — so a failed "Start reisen" attempt (network error path, `catch` block at line 422-425) leaves the user on step 12 with `error` set, but the draft has ALREADY been deleted from localStorage (since `step` became 12 the moment they navigated there). **If the user then refreshes the page after a failed submission, all their answers are gone.**

### Consequence 2 — No server-side validation of intermediate step data; a determined client can skip required steps entirely

- Because the UI never calls any per-step save/validate endpoint, and validation (`validate()` functions in `Step1Profile.tsx`, `Step3Tilknytning.tsx`, `Step4Kjærlighetsspråk.tsx`, etc. — confirmed present in nearly every step file via `list_code_definition_names`/grep) is **entirely client-side JavaScript** gating the "Next" button's `disabled` state, a user (or a script) can bypass all of it by calling `POST /api/profile/setup` directly with a crafted payload.
- `app/api/profile/setup/route.ts` DOES apply server-side Zod validation via `validateOnboarding()` (`lib/validation/onboarding-setup.ts`) — this is good — BUT:
  - Only `basic` (Step 1 fields) is a **required** top-level key in `onboardingSetupSchema` (`lib/validation/onboarding-setup.ts` line 196: `basic: basicProfileSchema` — no `.optional()`). **Every other section is `.optional()`**: `personlighet`, `livssituasjon`, `tilknytning`, `kommunikasjon`, `kjaerlighet`, `livsstil`, `relasjonsStil`, `fremtid`, `humor`, `grenser`, `moden`, `preferanser` (lines 197–208).
  - This means a client can submit **only the Step-1 "Grunnprofil" fields** and successfully complete onboarding (`onboardingComplete: true`, `deepProfileComplete: true` are set unconditionally in `app/api/profile/setup/route.ts` at the end of the handler, with no check that any of steps 2–12 were actually filled in). **All 12 remaining "deep profile" steps (personality, life situation, attachment, love language, values, relationship style, future vision, humor, boundaries, maturity) can be skipped entirely by calling the API directly**, despite the UI enforcing per-field minimum-length validation (e.g., `personlighetSchema.selfDesc` requires min 10 chars, but only within the optional wrapper, so omitting the whole `personlighet` key skips that check entirely).
  - This directly contradicts the core business rule stated in the comment header of `app/api/onboarding/complete/route.ts` (the dead endpoint): *"Core-definition: Bare brukere med fullført djup profil kan få match"* (Only users with a completed deep profile can get matched) — that rule is enforced in the (unused) `/api/onboarding/complete` route via `DEEP_STEPS.every(...)`, but is **completely absent** from the actually-used `/api/profile/setup` route.
- **Separately**, `app/api/onboarding/save/route.ts` (the dead route) DOES do proper defensive validation of `step` against `DEEP_STEPS` enum values and rejects invalid steps — but since it's never called, this protection is moot.

### Minor / secondary onboarding issues

- `OnboardingFlow.tsx` lines 296–426 build a large `payload` object referencing `data.structureSpontaneity` and `data.introExtrovert` twice under two different top-level keys (`kommunikasjon.commStyle`/`conflictStyle` at lines 322–323, and again under `preferanser.structureSpontaneity`/`introExtrovert` at lines 356–358) — duplicated/overloaded field usage that risks confusing data semantics (same raw answer mapped to two different logical concepts: "communication style" AND "structure vs spontaneity preference").
- `handleStartReisen()` has three different exit paths after a successful `/api/profile/setup` call (lines 368–421): (a) if no `userId` returned AND no `onComplete` callback → redirect to `/dashboard`; (b) if `onComplete` callback exists → call it and `return` (no matching/redirect at all in this branch, relying entirely on the parent `AppShell` to route); (c) otherwise, POST to `/api/match` and redirect to `/matching?userId=...`, or fall back to `/dashboard` if that fails. This 3-way branching is fragile: the "matching" trigger is fired from the onboarding flow itself with a swallowed `catch` (line 419 `/* matching failed — fall through */`), so if `/api/match` fails for any reason, the user is silently redirected to `/dashboard` with no error shown and no retry — they may never actually be matched, and never know a match request failed.
- `Step1Profile.tsx` validation requires `age >= 23` and shows the error "Du må være minst 23 år" — but there is no App-level Terms-of-Service age-gate check anywhere else; this 23+ floor is enforced only in this one client component's `validate()` function and mirrored server-side in `basicProfileSchema` (`age: z.coerce.number().min(23, ...)`), which is good, but it means the ONLY server-side field-level validation that is actually enforced end-to-end is for the Step-1 basic fields — everything else is optional and effectively unvalidated server-side once wrapped in an omitted key.
- `OnboardingLayout.tsx` progress bar is described in the header comment as showing "progressbar + children" but no visual progress bar is actually rendered in the JSX (only a static "Fortsett i ditt eget tempo" text at lines 62–66) — the `progressPercent` prop passed in from `OnboardingFlow.tsx` (line 461) is computed but never displayed anywhere in `OnboardingLayout.tsx`. This is a UX/functional gap: users have no visual indicator of how many of the 13 steps remain, other than the `slideIndex`/`totalSlides` props passed into each individual `OnboardingSlide` (not verified further, but the intended top-level progress bar component appears to have been removed without removing the prop-plumbing).

## Chat Flow

### CRITICAL BUG — Every message sent through the live chat UI fails server-side Zod validation and is rejected with HTTP 400

This is the most severe functional defect found in the entire chat flow:

- The client (`app/chat/context/ChatContext.tsx`, `sendMessage()`, lines 125–151) always calls `POST /api/chat/send` with `type` set to either `"text"` (default, from `ChatContainer.tsx` `ChatInput.handleSend()` line 394: `sendMessage(text.trim(), "text")`) or `"image"` (line 434: `sendMessage(data.imageUrl, "image")`).
- The server route `app/api/chat/send/route.ts` validates the incoming body against `chatSendMessageSchema` (defined in `lib/api-validator.ts` lines 69–73):
  ```
  export const chatSendMessageSchema = z.object({
    conversationId: z.string().min(1, ...),
    content: z.string().min(1, ...).max(5000, ...),
    type: z.enum(['user', 'continue_choice']).default('user'),
  })
  ```
  **The Zod enum only accepts `'user'` or `'continue_choice'`.** It does **not** include `'text'` or `'image'` — the two literal values the frontend actually sends.
- Since `type` has `.default('user')` but the client is *explicitly* passing `"text"`/`"image"` (not omitting the field), Zod's `z.enum(...)` will **reject** the value outright (defaults only apply when the key is `undefined`, not when it's present with an invalid value) — `chatSendMessageSchema.safeParseAsync(...)` returns `success: false`.
- Result: `app/api/chat/send/route.ts` line 43–48 returns `errorResponse("Valideringsfeil: type: Invalid enum value...", 400)` for **every text message and every image message** sent from the actual UI.
- The `mapMessageType()` helper inside the same file (lines 24–32) is clearly designed to convert frontend types (`"text"|"image"|"task"|"choice"`) to Prisma's `MessageCategory` enum (`"user"|"system"|"continue_choice"|"image"`) — but this mapping function only runs **after** the Zod validation already rejected the request, so it is unreachable dead code for any request originating from the live UI. This looks like a very recent regression (the Zod schema was authored for an older/different `type` contract than the one the UI + `mapMessageType()` were built for) — either the schema was changed without updating the UI/mapper, or vice versa.
- **Practical impact**: assuming this codebase is deployed as-is, the chat feature is fundamentally non-functional for sending any message — a total send-flow break, not a partial degradation. This should be the #1 priority fix flagged by this audit.

### No real-time message delivery — Pusher/WebSocket infrastructure exists in the codebase but is NOT wired into the live chat page

- `components/chat/ChatRoom.tsx` and related realtime hooks referencing Pusher exist in the repo (confirmed via `grep -rl "components/chat/ChatRoom"` matching only doc archives and build caches — the component itself is not imported by any live route).
- The actual live chat route `app/chat/[id]/page.tsx` → `ChatPageClient.tsx` → renders `ChatProvider` (from `app/chat/context/ChatContext.tsx`) + `ChatContainer`. **`ChatContext.tsx` contains zero Pusher subscriptions, zero WebSocket code, and zero polling/interval logic for refreshing messages.** Messages are fetched exactly once on mount (`useEffect` on `conversationId` change, line 82–84) via `loadMessages()`, and thereafter only updated via optimistic local state pushes when the *current user* sends a message (`sendMessage()`, lines 137–146).
- **Consequence: if the partner sends a message, the current user's chat window will never show it until they manually reload the page or navigate away and back.** There is no live/real-time updating of the conversation at all in the shipped implementation, despite `usePresence` (see below) polling every 3 seconds for online/typing status — that polling covers presence only, not message content.
- This is a severe "reliability" gap relative to what a "chat" feature implies — recipients simply will not see new messages in real time.

### Presence/typing indicators rely on in-memory server state — broken across server restarts and multi-instance/serverless deployments

- `lib/presence/presenceState.ts` implements presence entirely with an in-process `Map<string, PresenceState>` (line 22) plus `setTimeout`/`setInterval` for auto-clearing typing state and periodic cleanup (lines 68–96, 148–155).
- Comment at the top of the file self-acknowledges this: *"Merk: Dette er in-memory, så state mister ved server restart. For production med flere Node-instanser, bruk Redis eller DB."* (Note: this is in-memory, so state is lost on server restart. For production with multiple Node instances, use Redis or a DB.)
- On any horizontally-scaled or serverless deployment (e.g., Vercel functions, multiple containers), presence/typing state will be inconsistent because different requests may hit different server instances, each with its own isolated `presenceMap`. `usePresence` (`hooks/usePresence.ts`) polls `/api/presence/get/[id]` every 3 seconds (lines matching `setInterval(fetchPresence, 3000)`), so a user's "online"/"typing" indicator will flicker or simply show stale/incorrect data depending on which instance serves each poll.
- This is a known, documented architectural limitation (self-documented in code) but is worth flagging as a functional reliability risk for anything beyond a single-instance dev/demo deployment — and per `docs/SECURITY-STABILITY-PLAN-v1.md` item #9, there is a known "Duplisert VIPPS OAuth & Pusher+Supabase overlapping" architecture smell suggesting Pusher infra exists elsewhere in the codebase but isn't unified with this presence system either.

### Missing read receipts — schema supports it, but nothing sets it

- `prisma/schema.prisma` `Message` model has `state MessageState @default(SENT)`, `deliveredAt DateTime?`, and `readAt DateTime?` fields, and a full `MessageState` enum (`SENT | DELIVERED | READ | DELETED`).
- **None of these fields are ever written to** — `app/api/chat/send/route.ts`'s `prisma.message.create()` call only sets `id`, `conversationId`, `senderId`, `content`, `type` (lines 74–81); it never sets `state`, `deliveredAt`, or `readAt`. There is no separate "mark as read" endpoint anywhere under `app/api/chat/` (confirmed via `search_files` for `readAt|isRead|read_receipt|markAsRead` in `app/api/chat` — zero results).
- Consequently, every message is permanently stuck at `state: SENT` in the database forever, and the UI has no way to render read-receipt indicators even though `MessageBubble.tsx` has infrastructure for showing a small "Resonans" (resonance) indicator (lines 462–480) that is unrelated to read state. Read receipts are a fully missing feature, not just an unimplemented UI affordance — the backend never records the data needed to support it.

### Empty-message handling

- Client-side: `ChatInput.handleSend()` (`ChatContainer.tsx` line 380–381) checks `if (!text.trim() || sending) return;` — correctly prevents submitting whitespace-only or empty messages from the UI.
- Server-side: `chatSendMessageSchema.content` requires `.min(1, 'Melding kan ikke være tom')` (`lib/api-validator.ts` line 71) — this correctly rejects empty `content` server-side too (this part of validation is fine; only the unrelated `type` enum mismatch described above breaks the whole endpoint).
- No server-side `.trim()`/whitespace normalization is applied to `content` before the `min(1)` check — a message consisting purely of spaces/newlines (e.g., `"   "`) would pass Zod's `min(1)` (string length ≥ 1) and be stored as a "blank-looking" message in the database, since `z.string().min(1)` only checks length, not whitespace content. This is a minor edge case gap: whitespace-only messages can be persisted even though the intent is clearly to block empty sends.

### Image upload edge cases

`app/api/chat/image/route.ts` — mostly solid, but has notable gaps:
- **Type validation is done ONLY via the browser-supplied `file.type` MIME string** (line 64: `if (!ALLOWED_TYPES.includes(file.type))`), which is client-controlled metadata, not derived from actual file content/magic-bytes inspection. A malicious client can rename/relabel any file (e.g., an HTML file with an XSS payload, or an executable) with a spoofed `Content-Type: image/jpeg` header in the FormData part and it will pass this check, since the server never inspects the actual byte content of the uploaded file. Combined with the fact the file is written directly into `public/uploads/images/{conversationId}/` (a publicly web-servable static directory), this is a stored-content risk: e.g., an uploaded file with a spoofed image MIME type but actually containing HTML/JS could potentially be served back with a MIME type that a browser might still sniff/execute in some legacy browsers, depending on how Next.js's static file server sets `Content-Type` headers for the `/uploads/` path (not verified in this pass, but worth flagging).
- Size validation (`MAX_FILE_SIZE = 5MB`, line 15/72) is correctly enforced server-side — good.
- Filenames are safely UUID-randomized (`randomUUID()`, line 109) — this avoids path-traversal / filename-collision issues, and the code additionally double-checks `uploadDir.startsWith(...)` (lines 115–121) as defense-in-depth against conversationId-based path traversal — this is good practice.
- However: `conversationId` itself is taken directly from `formData.get('conversationId')` and used to build a directory path (`path.resolve(process.cwd(), 'public', 'uploads', 'images', conversationId)`, line 113) BEFORE the `startsWith` safety check — if `conversationId` contains something like `../../etc` it would be resolved and only rejected *after* `path.resolve()` already computed the (possibly out-of-bounds) absolute path; the check does correctly catch this before the `mkdir`/`writeFile` calls, so no filesystem write actually happens outside `public/uploads/` — this specific vector is closed, but it depends entirely on the `startsWith` guard being present and correct, which it is here. No further exploit path was found, but the API also doesn't validate that `conversationId` matches Prisma cuid format before using it as directory-path input, relying solely on the post-hoc string-prefix guard.
- On the frontend, `ChatInput.handleImageUpload()` (`ChatContainer.tsx` lines 411–443) does **not perform any client-side type or size check before uploading** — it relies entirely on the `accept="image/jpeg,image/png,image/webp"` attribute on the `<input type="file">` (line 472), which is a soft UI hint only and is trivially bypassable (e.g., via drag-and-drop of any file type, or by changing the accept filter in devtools). All real validation happens server-side (which is correct in principle), but the UX for a rejected/oversized upload is poor: on failure, the code only does `console.error('Bilde-opplasting feila:', err); return;` (lines 428–430) — **no user-facing error message is shown at all** when an image upload fails (wrong type, too large, network error, or unauthorized). The user just sees the upload silently do nothing, with no toast/alert/inline error.
- `sendMessage(data.imageUrl, "image")` is called after a successful image upload (line 434) — but per the CRITICAL bug above, this call will also fail with the same Zod `type` enum 400 error, since `sendMessage` always POSTs `type: "image"` which is not in `['user','continue_choice']`. So even if the image itself uploads successfully to disk, the corresponding chat message referencing it will fail to be created — an image could be uploaded to `public/uploads/images/{conversationId}/` and never actually get linked into any conversation message, leaving orphaned files on disk with no DB record.

### Message ordering

- `app/api/chat/messages/route.ts` orders by `createdAt: "asc"` (line 30) — correct, chronological ascending order, good.
- However, `Message.id` is generated client-independent as `msg-${Date.now()}-${Math.random()...}` in `app/api/chat/send/route.ts` (line 76) rather than using Prisma's default `cuid()` (the schema default is `@id @default(cuid())` per `prisma/schema.prisma`, but this custom `id` explicitly overrides that default). Using `Date.now()`-based IDs combined with `Math.random()` is a minor but real risk: if two messages are created within the same millisecond by concurrent requests (e.g., rapid double-click send, or two browser tabs), the random suffix mitigates outright collision, but this pattern is unusual and unnecessary given Prisma already provides collision-resistant cuid generation — no evidence of an actual ordering bug from this, but it's a code smell that increases collision risk over time under load.
- Optimistic client-side ordering: `ChatContext.sendMessage()` appends the new message to local state immediately (lines 137–146) using `data.message.id` from the server response — since the send API is currently broken (see CRITICAL bug), this optimistic-append path can never actually succeed in the current code, so no messages ever get added client-side after the initial load; the chat UI is effectively frozen after the first `loadMessages()` call for any user who tries to send anything.

### XSS risk in message rendering

- `grep` for `dangerouslySetInnerHTML` across `app/chat` returned **zero results** — message content is rendered via plain JSX text interpolation (`MessageBubble.tsx` line 454: `{content}`), which React auto-escapes. **No `dangerouslySetInnerHTML` usage found in chat components — this is good and mitigates classic reflected-content XSS via message text.**
- Image messages (`MessageBubble.tsx` lines 294–327) render `<img src={imageUrl} ...>` where `imageUrl` comes from `metadata?.imageUrl || content` — since `content` for image-type messages is exactly the `imageUrl` string returned by `/api/chat/image` (a same-origin `/uploads/images/...` relative path), this is not directly attacker-controlled in the current flow (the URL is server-generated, not user-typed), so no `javascript:` URI injection risk via this path was identified. However, since regular `sendMessage(text, "type")` calls in `ChatContext.tsx` accept unvalidated free-text `content` for `type: "image"` in principle (nothing server-side restricts an "image" type message's `content` field to actually be a valid uploaded-image path — the mapping in `mapMessageType()` just changes the Prisma category label, it doesn't validate the URL), if the broken Zod-validation bug above were fixed naively (e.g., by simply adding `'text'`/`'image'` to the enum) without adding a URL-format check on `content` for image-type messages, a user could send an arbitrary string as an "image" message and have it rendered as an `<img src="...">` tag with attacker-controlled `src` — while this doesn't execute JS directly via `<img src>`, it could still be used for basic data exfiltration (referrer leaking to attacker server) or UI spoofing. Flagging this as a **latent gap to address alongside the Zod fix**, not a currently-exploitable XSS given the send flow is already broken.

### BliKjentPanel — separate feature, largely disconnected from the main send flow

- `app/chat/components/BliKjentPanel.tsx` fetches guided questions via `GET /api/questions` and `GET /api/questions?categoryId=...` — this works independently and doesn't call `/api/chat/send` directly in the parts reviewed. Its "toggle" button in `ChatContainer.tsx` (line 522–524, the 📖 icon in `ChatInput`) has an empty `onClick` with just a comment `// Trigger BliKjentPanel — handled in parent` — meaning this particular icon inside the input bar is a **non-functional dead button**; the actual BliKjentPanel is opened only via the header toggle (`onOpenBliKjent` passed to `ChatHeader`), so the input-bar 📖 icon does nothing when clicked, which is a small but real dead-UI-element bug.

### `ChatInput` sender/partner ID plumbing gap

- `ChatContainer.tsx` line 654: `senderId={undefined} // TODO: Hent fra session/context` — the `senderId` prop passed into `ChatInput` (used for image uploads at line 419-420: `formData.append('senderId', senderId)`) is **hardcoded to `undefined`** with an explicit `// TODO` comment. Since `handleImageUpload()` guards with `if (!file || !conversationId || !senderId) return;` (line 413), **image uploads can never actually be triggered from `ChatContainer` in its current state**, because `senderId` is always `undefined`, so the guard clause silently no-ops the entire upload handler regardless of `imageShareAllowed`. This means the image-sharing feature is completely non-functional from the live chat UI today, independent of the server-side image-route logic being otherwise correct — the client never even attempts the upload because of this unset prop.
